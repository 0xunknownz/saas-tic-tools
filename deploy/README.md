# Test-environment deployment (single host)

This directory is generated by `saasctl init`. It deploys the Product to **one host for the
internal test environment, with test data only** (PRD AC-027). It is not a private-deployment,
production or air-gapped package; those are later milestones (technical design 15).

Layout:

| Path | Purpose |
|---|---|
| `deploy/compose/test.yaml` | PostgreSQL, one-shot migration, API, worker, Web, nginx edge |
| `deploy/docker/api.Dockerfile` | API + worker + migration runner image |
| `deploy/docker/web.Dockerfile` | TanStack Start SSR image |
| `deploy/docker/edge.Dockerfile` | Admin SPA, tenant admin SPA + nginx reverse proxy |
| `deploy/docker/nginx.conf` | Edge routing; download paths disable proxy buffering |
| `deploy/migrate/` | Migration runner used by the one-shot service and `MIGRATE_ON_START` |
| `deploy/scripts/up.sh` | build, migrate, start; refuses to start the API if migration fails |
| `deploy/scripts/down.sh` | `docker compose down` (keeps volumes) |
| `deploy/scripts/smoke-test.py` | login + create tenant/member through the public edge |
| `deploy/.env.example` | every variable, no secrets |

## Prerequisites

- Docker with the `compose` plugin, and network access on the host that builds the images
  (Go modules and npm packages are downloaded during `docker compose build`).
- Go 1.26 on `PATH`. There is no separate `saasctl` install to keep in sync: `apps/api/go.mod` pins the
  module version and `go tool` builds exactly that version for `go tool saasctl build`, `db migrate`
  and `admin bootstrap issue`.
- A read-only token for the private Foundation repository in `deploy/.env` as `FOUNDATION_READ_TOKEN`,
  unless the build uses a vendor tree. The image build mounts it as a BuildKit secret
  (`docs/foundation-modularization.md` 5.3); it is never stored in an image.
- `python3` for `deploy/scripts/smoke-test.py`.
- Linux/amd64 or Linux/arm64 host. Use an image tag that matches the host architecture.

## Deploy

```bash
cp deploy/.env.example deploy/.env
# edit deploy/.env: at minimum POSTGRES_PASSWORD, SECRETS_KEY, MIGRATE_DATABASE_URL, *_IMAGE, TARGET_PLATFORM
#   openssl rand -base64 32        # SECRETS_KEY

sh deploy/scripts/up.sh
```

(The generated files are not executable by default; invoke the shell scripts with `sh`, or
`chmod +x deploy/scripts/*.sh` once.)

`up.sh` performs these steps, in this order:

1. `go tool saasctl build` — validates the composition, compiles `apps/api`, writes
   `release/manifest.json` and `release/migrations/plan.json`.
2. Starts PostgreSQL only, and waits for its health check.
3. Runs `go tool saasctl db migrate --yes` with `DATABASE_URL=MIGRATE_DATABASE_URL`. **If this fails the
   script exits non-zero and does not start any application container.**
4. Builds the stack images with `docker compose build` — **always**, not only when a tag is
   missing: `up` alone would silently reuse a stale `API_IMAGE`/`WEB_IMAGE`/`EDGE_IMAGE` after a
   source change (#110). Unchanged layers are cached by BuildKit, so a no-change re-run costs
   seconds, and a broken Dockerfile now fails the script instead of starting old images.
5. Starts the stack with `--force-recreate`: a rebuilt image behind an unchanged tag does not
   make compose restart a healthy container, and the #110 field test confirmed the stale
   container keeps serving. The one-shot migrate service re-runs as a no-op. The API and worker
   additionally declare `depends_on: migrate: condition: service_completed_successfully`, so even
   a direct `docker compose up` cannot start the application on a failed migration.

The edge is served at `http://localhost:${HTTP_PORT}` (default 8080):
Admin at `/admin/`, tenant admin at `/console/`, Web at `/`, API at `/api/`, liveness `/healthz`, readiness `/readyz`.
The tenant admin must stay on the Web host: the tenant session cookie is `__Host-tenant_session`, which a
separate hostname could not read.

After `up.sh`, create the first platform administrator from its printed single-use link, or run:

```bash
go tool saasctl admin bootstrap issue --email root@example.com \
  --operator deploy --admin-url http://localhost:8080/admin
```

(`DATABASE_URL` must point at the exposed PostgreSQL port, as in `MIGRATE_DATABASE_URL`.)

## Verify the deployment

```bash
set -a; . deploy/.env; set +a
export DATABASE_URL="$MIGRATE_DATABASE_URL"
python3 deploy/scripts/smoke-test.py --base-url "http://localhost:${HTTP_PORT:-8080}"
```

The smoke test bootstraps the first platform administrator (redeem, password, TOTP, login, MFA), creates a
tenant through the Admin API, accepts the first tenant-administrator invitation, invites and registers a
regular member, and checks the Admin SPA is served. It writes `release/smoke-result.json`.

Stop the stack with `sh deploy/scripts/down.sh` (add `--volumes` to delete test data).

## Variables

All variables live in `deploy/.env` (see `deploy/.env.example`). The API only reads environment
variables (technical design 12.2).

| Variable | Meaning |
|---|---|
| `POSTGRES_DB`, `POSTGRES_USER`, `POSTGRES_PASSWORD`, `POSTGRES_PORT` | test database; port is bound to 127.0.0.1 only |
| `MIGRATE_DATABASE_URL` | host-side URL used by `go tool saasctl db migrate` / `admin bootstrap issue` |
| `SECRETS_KEY` | 32 random bytes, base64; seals TOTP secrets and signs download links |
| `HTTP_PORT` | published edge port |
| `WEB_PUBLIC_URL`, `ADMIN_PUBLIC_URL` | public URLs used in e-mails and printed links |
| `API_IMAGE`, `WEB_IMAGE`, `EDGE_IMAGE`, `TARGET_PLATFORM` | image tags and the platform recorded in the Release Manifest |
| `STORAGE_PROVIDER`, `STORAGE_MAX_FILE_SIZE` | storage; `local` is test/development only (11.15) |
| `NOTIFICATION_PROVIDER`, `SMTP_*` | transactional e-mail; `disabled` keeps e-mail in the outbox |
| `TENANT_SELF_SIGNUP`, `TENANT_SELF_SERVICE_CREATE` | runtime overrides of `product.yaml` |
| `MIGRATION_LOCK_TIMEOUT` | how long the one-shot migration waits for the database lock |

## Migration failure behaviour

A failed migration must block the application, and this template enforces it on every path:

- `deploy/scripts/up.sh`: the host-side `go tool saasctl db migrate --yes` runs before `compose up` and
  exits non-zero; no application container is created.
- `deploy/compose/test.yaml`: the one-shot `migrate` service exits non-zero, and `api`/`worker`
  depend on `service_completed_successfully`; Compose never starts them.
- `deploy/scripts/entrypoint.sh`: with `MIGRATE_ON_START=true` (single-container runs) the image
  runs `/app/migrate` before the requested process and exits non-zero on failure.

The image does not carry the `saasctl` CLI. Instead it builds `deploy/migrate`, which applies the
exact `release/migrations/plan.json` written by `go tool saasctl build`. The container runner and
`go tool saasctl db migrate` use **the same plan, the same `saasctl_migrations` history table, the same file
checksums and the same database advisory lock**; they are interoperable in both directions and
parallel runs cannot apply a migration twice. This was verified against one database (see
`docs/review/m3-deploy-release-evidence.md` in the Starter). The host script `up.sh` uses the real
`go tool saasctl db migrate`; the one-shot compose service uses the in-image runner. Reproduce:

```bash
set -a; . deploy/.env; set +a

# Direction 1: the host CLI applies the plan; the container runner must agree.
DATABASE_URL="$MIGRATE_DATABASE_URL" go tool saasctl db migrate --yes
docker compose --env-file deploy/.env -f deploy/compose/test.yaml run --rm --no-deps migrate
# expected: "database is up to date"

# Direction 2 (fresh database): the container applies the plan; saasctl must agree.
docker compose --env-file deploy/.env -f deploy/compose/test.yaml run --rm --no-deps migrate
DATABASE_URL="$MIGRATE_DATABASE_URL" go tool saasctl db migrate --yes
# expected: "database is up to date"
```

## Download path and proxy buffering

Downloads must stop promptly when authorization is revoked (technical design 11.15). A buffering
reverse proxy hides that revocation from the client, so `deploy/docker/nginx.conf`:

- sets `proxy_buffering off` and `proxy_request_buffering off` on `/api/tenant/v1/files/<id>`
  and `/api/tenant/v1/files/<id>/content`;
- forwards the API's `X-Accel-Buffering: no` header unchanged (the application sets it too);
- uses HTTP/1.1 with an empty `Connection` header so each download is an independent stream.

If you replace nginx with Caddy or a cloud load balancer, the same requirement applies: disable
response buffering on the download paths and limit per-connection buffering. Measured client
backlog on the test host is recorded in `docs/review/download-revocation-spike.md` in the Starter.

## Request tracing at the edge

Every request gets one correlation id, shared by the edge access log, the API access log and the
response header (TRACE-05). The shipped nginx configs:

- generate one when the client sent none (`map $http_x_request_id $req_id { "" $request_id; }`)
  and reuse a well-formed `X-Request-ID` from an outer proxy;
- forward it to the API on `/api/`, the download path, `/healthz` and `/readyz`;
- hide the upstream header and re-add it with `add_header ... always`, so exactly one
  `X-Request-ID` reaches the browser, including edge-generated 502/504 responses;
- log it as `rid=` in the access log, so an edge-only failure (timeout, 502) can still be
  matched with a support case even though the API never saw the request.

If you replace nginx with Caddy, a cloud load balancer or a Kubernetes ingress, keep the same
contract: accept or generate a 32-character lowercase hex id, pass it to the API as
`X-Request-ID`, echo exactly one back, and include it in the access log. An id supplied by a
client is a correlation hint only; the API never treats it as a credential.

## Test licence for the composed test environment

A composition that includes the licence module starts in **Missing** state, which blocks every
write (D-011). That is correct for a real deployment but left §deploy/scripts/smoke-test.py§
unable to create tenants with §--modules all§ (issue #109). §up.sh§ now installs a **24-hour
signed test licence** in that case, through the product's own licence importer
(§deploy/scripts/test-license.sh§):

- an ephemeral Ed25519 key is generated inside the fixture process; the private key is never
  written to disk, and the public key is recorded in a clearly marked managed block in
  §deploy/.env§;
- the licence is signed for THIS product id and instance (§test-instance§ by default), valid 24
  hours, features §advanced§, generous test limits;
- if §LICENSE_VERIFICATION_KEYS§ is already configured, or the composition has no licence module,
  or §APP_ENV§ is not §development§, the script refuses and nothing changes;
- after expiry, writes are blocked again — reset the test volume (§docker compose ... down -v§)
  and re-run §up.sh§ for a fresh one. Remove the managed block to revoke the keys.

This is a test-environment tool only. Private deployments keep the real flow: a customer licence
is signed by the vendor key and imported through §POST /api/admin/v1/license§; nothing in this
path touches or bypasses that.

## Known limitations (test environment only)

- `APP_ENV` is `development`: the API accepts only `development` or `production`, and `production`
  requires HTTPS public URLs and a production secret. Test deployments therefore run with test data
  and without secure cookies; **do not expose this stack to untrusted networks and do not put real
  data in it**.
- No TLS: nginx terminates plain HTTP. Add a TLS terminator before any use outside localhost.
- Single host, one API/worker replica; no high availability, backup, restore or upgrade procedure.
- Local storage provider and a local Docker volume; no object storage.
- E-mail is disabled unless SMTP is configured.
- Login throttling and self-signup rate limiting see the nginx address as the client address because
  the API does not yet consume `X-Forwarded-For`. This only affects test traffic.
- The Web image runs `vite preview` with the full pnpm workspace; it is not a hardened production
  server image. The Admin SPA is served by nginx under `/admin/`.
- Image builds require network access (Go modules, npm packages, base images). For an air-gapped
  environment use the later private-deployment package.

## Release Manifest

`go tool saasctl build` writes `release/manifest.json` (technical design 14.3, first-stage fields):
Product ID/version/git commit, Foundation Go module and Admin versions, Foundation Plugin Contract,
Admin Contract, normalized plugin composition with its digest and an ordered plugin ID+version
digest, database migration version/count/digest, security suite result, and build time/platform/
image tag/artifact directory. `release/migrations/plan.json` is the ordered migration plan used by
the image.

CI appends the security suite result without losing the rest of the manifest:

```bash
go tool saasctl build --security-result scripts/security/report.json
```

The report file may contain `{"securitySuite": {...}}` or the fragment directly; see
`docs/review/m3-deploy-release-evidence.md` in the Starter for the exact field list.
